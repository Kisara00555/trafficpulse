# Part 3 — Start with a fair baseline

Today we examined only the training years and compared three simple forecasts on 2017 validation data. The final test file was never opened. This matters because looking at the final answers while choosing an approach would make the eventual test less honest.

The training set has 25,329 observed hourly counts. Its average is about 3,253 vehicles per hour, but a single average ignores the repeating weekday and time-of-day pattern. On the same 8,667 eligible validation hours, the weekday-and-hour training average had MAE 279.1 vehicles/hour; using the exact count from one week before had MAE 302.6; and one overall training average had MAE 1,742.8. Lower MAE is better. The weekly-lag reading was present for 99.5% of observed validation targets. The other 46 were left out of this shared comparison rather than filled in.

We added a standard-library analysis program, a test that rejects final-test inputs, a reproducible JSON result, two labeled SVG charts, and an executed notebook. The notebook reads only the training and validation CSVs. All 20 unit tests passed; the notebook ran top to bottom and its saved structure and output checks passed.

This comparison covers one historical station and one validation year. It does not establish future or real-world performance. The source clock is still timezone-ambiguous, and the one-week baseline cannot score hours whose lag is missing. After execution, I reviewed the notebook on GitHub: the tables and both charts rendered with their units and sample counts, and I shortened the code cells so they no longer need horizontal scrolling.
